# How Payee Sentinel uses Meko

Meko is the only place the agents share anything. Each agent keeps its own conversation; what one agent learns reaches
another only through memory in a Meko datapack. This page maps every Meko feature to the code that uses it, and says
plainly which features are not used by the agents yet.

## Used by the agents today

| Meko feature | What Payee Sentinel does with it | Code |
|---|---|---|
| **Datapacks** (REST `POST /datapacks`) | Four separate datapacks, as theme 03 suggests: `sentinel-signals` (raw risk signals and the analyst's resolutions), `sentinel-patterns` (attack patterns a person approved), `sentinel-legit` (legitimate look-alikes a person confirmed), `sentinel-audit` (decision records) | `agents.py`, `Memory.__init__` |
| **Conversations** (`conversation_create`) | One conversation per agent; the payments agent starts a new one at every payment run, so it begins with no history and must find what matters in memory | `Memory.conversation`, `Memory.new_session`, `story.py` `run_payments` |
| **Decision traces** (`conversation_add_message` with `reasoning`, `plan` and `metadata`) | Every decision, allow included (a bank change applied, a payment released, a step-up call, a hold, a block, a freeze), is saved as a turn with its reasoning, its plan and the retrieval behind it: the query the agent ran, the datapack and the ids of the memories it found. Meko's documentation says its portal shows these turns as decision traces (we have not opened that view yet). Walkthroughs of six decisions, the last one across two companies: `docs/TRACES.md` | `story.py`, `Lane._decision`; `scripts/trace_walkthroughs.py` |
| **Memory** (`memory_add` with JSON metadata) | Each risk signal an agent sees (type, vendor, time, weight, evidence) — the core of the shared memory; the analyst's verdicts ("attack confirmed", "legitimate"), so closed cases stop raising alarms; decision records, so the auditor can find them later; pattern candidates | `Memory.write`, `Memory.resolve`, `Memory.record_decision`, `evaluate.py`, `story.py` |
| **Memory search** (`memory_search`, hybrid) | Before every bank-change and payment decision an agent searches the vendor's signals from all agents; the auditor searches decision records and signals to explain a case | `Memory.signals`, `Memory.history`, `Memory.decisions` |
| **Learnings and promotion** (REST `POST /promote-memories`) | After a confirmed attack the auditor writes a pattern candidate; a person presses "Promote" and it becomes collective memory. In learning v2, legitimate look-alikes a person confirms are promoted the same way | `story.py` `Story.promote`, `evaluate.py`, `context/meko.py` |
| **Collective memory** (`memory_get_all` with `promoted=True`) | Before acting, agents check approved patterns; a match freezes a vendor's bank details before anyone asks to change them | `Memory.patterns`, `Memory.legit_patterns`, `Agent._check_patterns` |
| **Knowledge base** (`knowledgebase_upload_document`, `knowledgebase_search`) | The company's payment policy and fraud playbook (`payee_sentinel/knowledge/`, invented) are uploaded to `sentinel-patterns` when the demo starts; the auditor quotes the passage behind the rule it explains | `story.py`, `Story.__init__`, `Story.explain` |
| **Artifacts** (`artifact_put`) | The auditor keeps each case report as an artifact in `sentinel-audit` (content-addressed: the same report gives the same hash) | `story.py`, `Story._save_report` |
| **Context search** (`context_search`) | When a bank-change request arrives, the vendor-master agent asks Meko in plain words whether the new account or device appeared in an earlier confirmed case, across memory, knowledge base and past conversations at once. Meko answers with a grade (`match_quality`: high, mid or low) and a hint for the agent. A case file Meko returns counts only for what it shares with the request, checked in its text: the same account, the same device, or a new account in the same country (a similar case). The answer goes into the decision's trace, while the decision stays with the rules | `story.py`, `Lane._ask_about_request`, `Lane._link` |
| **Self-learning loop** (`selflearning_status`, `selflearning_query_log`, `selflearning_verify`) | Meko logs and grades every `context_search`. Once a case is confirmed, the auditor agent reads Meko's self-learning status, finds the vendor-master agent's question in Meko's search log, adds what was missing (the confirmed case file, to the knowledge base) and asks Meko to replay the question. In the demo, on the simulator, the question goes from mid to high, and the next week the same question about Bergmann's request points to the Nordwind case as a similar one. On real Meko, in the clean pass recorded on 9-Nov, the demo's own question went from low to mid (`outcome: improved`), not to high; the week-2 question pointed to the Nordwind case as a similar one, as offline. A probe with a similar question and a hand-written case file had gone from mid to high (`docs/MEKO_SMOKE.md`) | `story.py`, `Story.self_learning`, `Story._case_file` |
| **Postgres inside the context** (Meko AMP: `amp_core_budget`, `amp_cluster_create`, `amp_branch_list`, `amp_compute_list`) | The Meko lane's system of record lives in a Postgres cluster inside the `sentinel-audit` datapack: the vendor master with every change on file, the bank-change requests and the payments. Every row a decision makes carries the id of that decision's trace in Meko, so a record and its reasoning point at each other. The analyst calls "the number on file 60 days ago" through an *as of* query on the vendor master's history: the current phone is the attacker's, the one on file 60 days earlier is the vendor's. Created on 9-Nov-2026 with Alessandro's yes (`payee-ledger`, PostgreSQL 18.2, one writer endpoint of 0.5 vCPU and 4 GiB, the Free tier's whole budget, reachable over SSL from one IP only; the password went straight into `.env`). A full story runs 32 queries, about 0.12 s each. Where the database cannot be reached (the public demo, a replay elsewhere, the tests) the same schema runs on SQLite in memory; the decisions never depend on which | `ledger.py`; `story.py`, `Lane.review`, `Story._ledger_lines`; `app.py` |
| **Sharing context between companies** (a `consortium` datapack; in the demo, simulated in one place) | Week 3 of the demo and round 5 of the measurement. When a member's analyst confirms an attack, the account, phone and device its own systems logged go into a shared `consortium` datapack, each entry with the company, the case and the id of the decision trace behind the stop. The attack patterns a person approved go into every member's collective memory, and the confirmed case files into their knowledge base. The next member's agents read the list back from Meko and add `consortium.known_infrastructure` (+6, fixed before round 5 ran) when a value comes back; its vendor-master agent's `context_search` finds the other company's case file. Raw signals, vendor data and payments stay inside each company. A member can take a case back: a revocation record goes into the same datapack, nothing is deleted, the list is read again without the case, and the agents skip the pattern from it (Meko cannot delete a promoted memory). Not run on real Meko yet: sharing one datapack between two Meko accounts has not been tried | `story.py` `Story.share`, `Story._share_list`, `Lane._check_known`; `evaluate.py` `run_consortium` |

These tools are on the live MCP server (57 tools on 9-Nov-2026, against 28 in the documentation we read on 8-Nov). The
self-learning ones were found by listing the server's tools; their descriptions say only `context_search` calls count.

## What we learned about Meko along the way
The live service and the offline simulator behave the same for everything above (`docs/MEKO_SMOKE.md`):
- metadata goes in as a JSON string;
- promoted memories leave `memory_search` and lose their metadata, so a pattern carries its signal types in its text;
- explicit `memory_add` text is stored as written, while memories extracted from conversations are rewritten by an
  LLM — and one was rewritten wrongly — so signals are always written explicitly;
- the whole demo story ran on real Meko in about a minute and reached the same decisions as offline — on a clean,
  quiet service. In nine rehearsals in a row right after it, new memories did not show up in searches in time, and
  the Meko lane lost like the siloed one. The cause, as far as we can measure it: a new memory is searchable at once,
  but for hours its score is about half its similarity, so near-identical copies from earlier runs outrank it
  (`docs/MEKO_SMOKE.md`). On empty datapacks this does not matter;
- what Meko learns stays learned: once a case file is in `sentinel-patterns`, a later demo run finds it in week 1
  too. A recording therefore needs a clean set of datapacks (clearing them deletes data, so it is Alessandro's call).
